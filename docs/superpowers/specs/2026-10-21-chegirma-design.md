# Chegirma — агрегатор скидок для Узбекистана. Дизайн-документ

**Дата:** 2026-10-21
**Рабочее название:** Chegirma (узб. «скидка»)
**Статус:** дизайн на утверждении

---

## 1. Намерение и «зачем»

В Узбекистане акции и скидки разбросаны по десяткам Telegram-каналов магазинов,
сайтам сетей, Instagram и OLX. Чтобы найти выгодную цену, человек должен сам
обойти все эти источники — это утомительно, и большинство выгодных предложений
проходят мимо. Telegram-каналы — фактически основной канал распространения акций
в стране.

**Идея:** приложение, которое само собирает все актуальные скидки из интернета по
всем категориям (от продуктов до стройматериалов) и показывает их пользователю в
одной ленте. Пользователь не ищет — приложение находит за него.

**Для кого:** массовый пользователь в городах Узбекистана, чувствительный к цене;
во вторую очередь — магазины, которым нужен канал продвижения акций.

## 2. Цели, не-цели, анти-цели

### Цели
- Единая лента актуальных скидок по всем категориям и городам Узбекистана.
- Автоматический сбор из множества источников без ручного труда пользователя.
- ИИ извлекает структуру скидки (товар, старая/новая цена, %, магазин, адрес, срок)
  из текста и из картинок (баннеры, листовки).
- Поиск по товару/бренду/магазину, карта ближайших скидок, список покупок с
  уведомлением «на твой товар появилась скидка».
- Три языка (узб. латиница, узб. кириллица, русский), валюта UZS.
- Работа на слабых устройствах и слабом интернете; кэширование ленты.

### Не-цели (пока не делаем)
- Онлайн-покупка/оплата внутри приложения (только ссылка/маршрут к источнику).
- Собственная доставка.
- Программа лояльности/кэшбэк.
- Сравнение цен по всем магазинам как отдельный ценовой движок (кроме проверки
  «фейковых скидок» по истории).

### Анти-цели (провал, даже если технически работает)
- Лента, забитая устаревшими и уже закончившимися акциями.
- «Фейковые скидки» (завышенная «старая» цена) без пометки.
- Дубли одной акции из сайта и Telegram рядом в ленте.
- Юридические/блокировочные проблемы из-за игнорирования robots.txt и ToS
  источников.
- Тормоза и высокий расход трафика на дешёвых Android-телефонах.

## 3. Ограничения и принятые решения по стеку

Решено пользователем:
- **Мобайл:** Flutter (iOS + Android, один код, хорошо на слабых устройствах).
- **Бэкенд:** Python / FastAPI. БД — PostgreSQL, кэш — Redis.
- **Первый результат:** сквозной срез end-to-end (один реальный источник →
  обработка → БД → API → приложение с лентой и карточкой на реальных данных).

Решено пользователем (после ревью дизайна):
- **Юридика сбора:** парсим публичные страницы и каналы, если это не запрещено
  robots.txt/ToS источника. Где ToS прямо запрещает скрапинг (Telegram/Instagram) —
  используем официальные API/боты или партнёрские договорённости, а не обход.
- **Модерация:** авто-публикация с флагами. Скидки показываются сразу; записи с
  низкой уверенностью ИИ или подозрением на фейк-цену автоматически помечаются
  (бейдж) или скрываются по порогу. Ручная модерация/админка — Фаза 4.
- **ИИ-бюджет:** ключ Claude есть, бюджет ограничен → контроль стоимости
  закладывается с Фазы 1 (см. ниже).

Решения, принятые автором дизайна (можно пересмотреть):
- **ИИ-обработка:** Claude API. Vision-модель читает баннеры/листовки и за один
  вызов возвращает структурированный JSON (название, старая/новая цена, %,
  магазин, адрес, срок). Отдельный OCR-пайплайн не нужен; Tesseract — запасной
  бесплатный вариант для простых случаев.
- **Планировщик парсеров:** Celery + Celery Beat (на Redis) — запуск сборщиков по
  расписанию каждые 1–3 часа, очереди задач, ретраи.
- **Админка и кабинет партнёра:** веб на FastAPI + серверные шаблоны (Jinja2) или
  лёгкий React — выбор отложен до фазы 4, на срез не влияет.
- **Живой источник для среза:** веб-парсер супермаркета (Korzinka/Makro — тот, у
  кого доступнее страница акций, с соблюдением robots.txt). Telegram-парсер
  (Telethon) — как шаблон; требует `api_id`/`api_hash` от заказчика.
- **Соблюдение правил источников:** перед парсингом проверяем robots.txt; где есть
  официальный API или партнёрская программа — используем их; соблюдаем разумные
  интервалы запросов и User-Agent.
- **Идентичность товара (`product_key`):** вычисляется как «магазин + нормализованное
  название» (нижний регистр, без стоп-слов/единиц измерения, фуззи-сопоставление) с
  сохранением оценки уверенности. Точный алгоритм и порог похожести — за билдером.
  Используется и для дедупликации, и для проверки фейк-скидок по истории.
- **Идентификация пользователя:** в Фазе 1 — анонимно по устройству (избранное и
  список покупок привязаны к устройству, без регистрации). Телефонная авторизация
  по SMS-коду (OTP) — в Фазе 2; выбор и оплата SMS-провайдера — отдельное решение
  заказчика на старте Фазы 2. Хранение ПДн — по законодательству РУз.
- **Карта и геокодинг:** тайлы OpenStreetMap через пакет `flutter_map` + геокодинг
  адресов через Nominatim (бесплатно, без привязки к платному Google Maps). Если
  точность по адресам РУз окажется недостаточной — пересмотр на платный провайдер.

## 4. Архитектура системы

```
┌──────────────────────── ИСТОЧНИКИ ─────────────────────────┐
│ Сайты магазинов │ Telegram-каналы │ Instagram │ OLX │ Кабинет│
│ (HTTP/HTML/API) │  (Telethon API) │  (где можно)│(API)│партнёра│
└───────┬──────────────┬──────────────┬─────────┬──────┬──────┘
        │              │              │         │      │
   ┌────▼──────────────▼──────────────▼─────────▼──────▼────┐
   │        СБОРЩИКИ (Celery workers, по расписанию)          │
   │  каждый источник → свой парсер → «сырой улов» (raw item) │
   └───────────────────────────┬─────────────────────────────┘
                               │ сырой текст + картинки
                   ┌───────────▼────────────┐
                   │   ОБРАБОТКА (ИИ)         │
                   │ • Claude: текст→JSON     │
                   │ • Claude vision: баннер  │
                   │ • категоризация          │
                   │ • дедупликация           │
                   │ • проверка фейк-скидок   │
                   │ • срок действия          │
                   └───────────┬─────────────┘
                               │ нормализованные Deal
                      ┌────────▼─────────┐
                      │  PostgreSQL + Redis │
                      └────────┬─────────┘
                               │
                      ┌────────▼─────────┐        ┌──────────────┐
                      │   FastAPI (REST)  │◄──────►│ Админка /     │
                      │  + авторизация    │        │ кабинет партн.│
                      └────────┬─────────┘        └──────────────┘
                               │ JSON API + push (FCM/APNs)
                      ┌────────▼─────────┐
                      │ Flutter-приложение │
                      │ (iOS + Android)    │
                      └────────────────────┘
```

**Поток сырой записи → скидки:**
1. Celery-воркер по расписанию запускает парсер источника.
2. Парсер отдаёт «сырой улов»: текст поста/карточки + ссылки на изображения +
   метаданные (магазин, URL источника, время).
3. Обработчик отправляет сырьё в Claude (текст и/или изображение) и получает
   структуру скидки в строгом JSON (через tool use / схему).
4. Нормализация: категория, город/филиал, парсинг дат, валидация цен.
5. Дедупликация (похожие записи из разных источников сливаются).
6. Проверка «фейка» по истории цен товара в этом магазине.
7. Сохранение/обновление `Deal` в PostgreSQL; инвалидация кэша ленты в Redis.
8. Триггеры уведомлений (список покупок, любимые магазины, гео).

**Контроль стоимости ИИ (бюджет ограничен):**
- Дешёвый пред-фильтр до Claude: отсекаем явный мусор и посты без признаков акции
  правилами/регулярками, не тратя вызов модели.
- Кэш по хэшу контента: одинаковый текст/картинка не обрабатываются повторно.
- Дешёвая модель (Claude Haiku) для простых текстовых случаев; сильная/vision —
  только для картинок и сложных постов.
- Батчинг и ограничение частоты; `raw_items` переобрабатываются только по явной
  необходимости.

## 5. Структура базы данных (первый набросок)

Основные таблицы (детали — на этапе плана):

- **stores** — магазин/сеть: `id, name, slug, logo_url, website, category_hint,
  is_partner`.
- **branches** — филиалы: `id, store_id, city, address, lat, lng, phone`.
- **categories** — дерево категорий: `id, parent_id, slug, name_uz_lat,
  name_uz_cyr, name_ru, icon`.
- **deals** — скидка: `id, title, description, store_id, branch_id (nullable),
  category_id, old_price, new_price, discount_percent, currency='UZS',
  image_url, source_type (website|telegram|instagram|olx|partner), source_url,
  starts_at, ends_at, status (active|expired|hidden|pending),
  is_promoted (реклама), is_fake_suspected, created_at, updated_at`.
- **price_history** — история цен для проверки фейков: `id, store_id,
  product_key, price, observed_at`.
- **raw_items** — сырой улов до обработки (аудит/повторная обработка): `id,
  source_type, source_ref, raw_text, raw_image_urls, fetched_at,
  processed (bool), deal_id (nullable)`.
- **users** — `id, phone/email, lang, city, created_at`.
- **user_categories** — интересы пользователя (many-to-many).
- **favorites** — сохранённые скидки и любимые магазины.
- **shopping_list_items** — товары, на которые ждём скидку: `id, user_id,
  query_text, category_id (nullable), active`.
- **devices** — push-токены: `id, user_id, platform, fcm_token`.
- **notifications** — журнал отправленных пушей.
- **partner_accounts** — кабинет партнёра: `id, store_id, login, role`.

Индексы под ленту (сортировка по %, по новизне, гео), полнотекстовый поиск по
`deals.title` (pg_trgm / tsvector) и справочник городов.

## 6. Экраны приложения (Flutter)

1. **Главная лента** — лучшие скидки дня; сортировка по % / новизне / близости;
   крупный красный бейдж «−30%»; бесконечная прокрутка; кэш для офлайна.
2. **Поиск** — по товару, бренду, магазину (напр. «цемент», «масло
   подсолнечное», «iPhone»); подсказки.
3. **Категории** — сетка с иконками.
4. **Карта** — магазины со скидками рядом; кластеризация пинов.
5. **Карточка скидки** — фото, старая/новая цена, %, магазин, срок, адрес; кнопки
   «Маршрут», «Поделиться в Telegram», «Открыть источник».
6. **Избранное** — сохранённые скидки и любимые магазины.
7. **Список покупок** — добавляешь товары, приложение уведомляет о скидке на них.
8. **Профиль и настройки** — язык (3), город, интересующие категории, тема
   (светлая/тёмная).

**Дизайн:** яркий, современный, акцент на цене и проценте; светлая и тёмная тема;
быстрая загрузка на слабом интернете.

## 7. Push-уведомления

- Скидка на товар из списка покупок.
- Новая акция в любимом магазине.
- «Горящие» скидки рядом (гео, с согласия пользователя).
- «Акция заканчивается завтра».

Транспорт: FCM (Android + iOS через APNs-мост).

## 8. Монетизация

- Платное продвижение акций (`is_promoted`, пометка «Реклама»).
- Кабинет партнёра для магазинов (самостоятельное добавление акций).
- Партнёрские ссылки на маркетплейсы (Uzum, WB, Yandex Market).

## 9. Поэтапный план (sizing: большой проект, фазами)

Строим не «всё сразу», а сквозными срезами. Каждая фаза — работающий результат.

- **Фаза 1 — Сквозной срез (первый результат).**
  Монорепо; FastAPI + PostgreSQL + Redis в Docker Compose; модель `Deal` и
  минимум справочников; один реальный веб-парсер (супермаркет) под Celery;
  обработка через Claude (текст→JSON) с базовой категоризацией и сроком действия;
  REST API ленты и карточки; Flutter-приложение с главной лентой и карточкой
  скидки на реальных данных; русский язык; инструкция по запуску.
- **Фаза 2 — Полный мобильный клиент.** Поиск, категории, карта, избранное,
  список покупок, профиль; 3 языка; светлая/тёмная тема; офлайн-кэш.
- **Фаза 3 — Источники и ИИ.** Telegram-парсер (Telethon), vision-обработка
  баннеров, дедупликация, проверка фейк-скидок по `price_history`, Instagram/OLX
  по мере допустимости.
- **Фаза 4 — Монетизация и админка.** Веб-админка модерации, кабинет партнёра,
  продвижение акций, партнёрские ссылки, push-уведомления.

Каждая фаза после утверждения этого документа оформляется отдельным планом
реализации (superpowers:writing-plans) и проходит обычный цикл разработки.

## 11. Юридические и этические рамки

- Перед парсингом каждого источника — проверка robots.txt и ToS.
- Где есть официальный API или партнёрская программа — использовать их.
- Разумные интервалы запросов, корректный User-Agent, без обхода защит.
- Instagram/соцсети — только там, где это допустимо правилами платформы.
- Хранение персональных данных пользователей — по законодательству РУз.
